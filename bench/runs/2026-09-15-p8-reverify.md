# P8 - O3 re-verification, 2026-09-15

The strategic phase: Joern's second graded objective. After a fix, a pattern matcher can say
"the text pattern vanished". The CPG can say whether the **locator still fires on the patched
method** - and when it does not, *why*: a guard now sits in the method's guard channel (or on
its class, or in a form it instantiates), or the sink itself is gone.

## What exists

- `rules/locators.sc` gains a `// @@ reverify` section: for one (file, method) it writes what the
  graph sees - guard tokens by family and **where** (`method:` / `class:` / `instantiated_class:` /
  `queryset_hook:` / `object_permission:`), sink counts (reads, exec reads/writes, dynamic writes,
  mapping iteration, multiplications, comparisons, ORM writes, control-dependent writes) and the
  route flag. A no-op on ordinary scans.
- `services/joern/reverify.py`: two modes, one function. **Preview** copies the whole target into
  scratch, applies the fix *there* (through `apply.apply_fix`, so the content guard applies), and
  rebuilds the CPG on the copy - the user's tree is untouched; the live tree is the "before".
  **Post-apply** rebuilds on the live tree with the first-Apply snapshot as "before". Both scans
  run with the same pack; the whole-target diff yields `regressions` (a fix that moves the bug
  is not a fix - TDD 8.9 step 4). `decide()` is pure and unit-tested.
- `POST /api/fix/verify {scan_id, path, function, rule_id, fixed_code?, start_line?, end_line?,
  original_code?}` → `{converged, locator_refires, fired_before, guard_present, guard_evidence,
  sink_present, regressions, reverify_method: cpg|pattern, mode: preview|post_apply, reason,
  evidence}`. Signed-in, scan ownership checked, `joern-*` findings only. Since the 2026-09-15
  review: `path` must stay inside the owned scan target (as must `/api/fix/apply` and `/revert`),
  `file` / `method` / `class` are validated as a relative `.py` path and identifiers and
  Scala-escaped before rendering, and the target method is class-qualified (`Class.method`).
- FixPanel: **Verify with CPG** next to Apply (preview) and **Re-verify with CPG** after Apply;
  a verdict line names the guard or says the locator still fires.
- Fallback: when Joern is not installed the endpoint answers with `reverify_method: "pattern"` -
  a token search over the patched function text - and says so in the reason.

## Exit gate: `orders.get_order` (shopfast bug 22), preview mode

| candidate fix | fired before | refires | guard evidence | converged |
|---|---|---|---|---|
| ownership check after the fetch (`row["user_id"] != current_user_id → PermissionDenied`) | yes | **no** | `method:permissiondenied` | **yes** |
| owner in the WHERE clause (`… AND user_id = ?`, `owner_id` param) | yes | **no** | `method:owner_id` | **yes** |
| cosmetic rename (`conn → connection`, `order_row`) | yes | **yes** | - | **no** - "the exploitable path is still there" |

The user's `testbeds/shopfast/orders.py` is byte-identical afterwards (asserted by the test).
Regressions 0 in every case. Script mode ×2 CPG builds: 83-92 s each.

## Through the API, server mode: `checkout` (djshop-dev bug 8, TOCTOU)

| candidate fix | converged | guard evidence | sink | ms |
|---|---|---|---|---|
| `transaction.atomic()` + `select_for_update()` (documented) | **yes** | `method:atomic`, `method:select_for_update`, `method:transaction` | write still control-dependent, now locked | 17,295 |
| conditional `UPDATE … stock__gte … F("stock") - qty` (documented) | **yes** | `method: f(`, `method:=f(` | no control-dependent write left (`sink_present: false`) | 13,075 |
| docstring says "atomic + select_for_update", code unchanged | **no** - still fires | - | - | 15,760 |

The third row is the P2 Fix-3 hazard doing O3's job: literals never reach the guard channel,
so a comment cannot verify a fix. 13-17 s per verification = two CPG builds on the sidecar.

## What "dominates" means here, honestly

The plan asked whether "the guard now dominates the sink". For TOCTOU that is exactly what
the P7 rule tests - the write is no longer control-dependent on an unlocked check - so the
silent locator *is* the dominance answer. For IDOR the ownership check legitimately comes
**after** the fetch (`row = fetch(id); if row.owner != me: 403`), so dominance of the read is
the wrong question; the evidence reported is the guard's presence and location in the P7
guard channels. `decide()` names the third case too: silent, no guard visible, sink still
there → "review by hand", never a silent pass.
