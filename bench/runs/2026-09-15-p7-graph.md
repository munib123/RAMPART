# P7 - the graph capabilities, 2026-09-15

Until today the four rules contained no graph traversal (August's "most important sentence").
P7 adds the three the plan scoped - and only those - and measures them on the DEV split, where
the P6 held-out analysis had classified five failure causes as structural.

## The probes, run for the first time (they were named in P0)

| capability | query | result on pysrc2cpg |
|---|---|---|
| control dependence | `call.nameExact("save").controlledBy` | returns the comparison CALL itself: `product.save()` ← `product.stock >= item.quantity`; shopfast's raw `UPDATE` ← `product["stock"] >= quantity`. Also: `CartItem.objects.create()` ← `qty <= 0` - an early-return validation is control dependence too, so ordering alone cannot separate the two |
| class scope | `method.typeDecl`, `typeDecl.ast.isCall.code`, `typeDecl.member.name`, `inheritsFromTypeFullName` | the class body is a `<body>` method: `permission_classes = [IsAuthenticated, IsOwner]` is a call; methods and attributes are MEMBERs; `IsOwner` and `AddToCartForm` are project TYPE_DECLs with inspectable bodies; bases resolve to `rest_framework\viewsets.py:<module>.ModelViewSet` |
| call graph | `method.callIn` | Flask `orders.get_order` ← `app.py:order` resolves across modules (name-based); Django views are never *called* - `urls.py` references them (`path("...", views.order_detail)` → field identifiers) |

## What changed in the Scala (`locators.sc`; see each run artifact's `rules_sha256` - the hash first quoted here was CRLF-computed, and rule hashes are now LF-normalised in `bench/backends/__init__.py`)

1. **TOCTOU = control dependence + receiver identity.** A write must be control-dependent on a
   comparison over a resource term, and - for an ORM write `x.save()` - `x` must be the object
   that was compared (`product.stock >= q` … `product.save()`). Raw SQL writes have no receiver
   and keep the token test. A comparison hidden in `a or b` is reached through the controlling
   node's AST.
2. **Class scope.** For a method in a class: the class body's calls and base names join the
   guard channel (so `LoginRequiredMixin` is authn evidence, `DjangoObjectPermissions` is authz).
   Since the 2026-09-15 review this is the class *body* only - member initialisers, a nested
   `Meta`, the bases - never sibling methods' bodies, so one method's ownership check cannot
   silence an IDOR in its siblings.
   For a *scoped read* (new slot `scoped_read_calls`: DRF `get_object`), two more things count as
   authorization: the guard text of the class's `queryset_hooks` (`get_queryset` scoping to
   `request.user`), and any class named in the body that defines an `object_permission_hooks`
   member (`has_object_permission`) - a cross-file type lookup. A direct `Model.objects.get()` in
   the same class still fires: DRF never runs the object permission for it.
   For the quantity rule: the body of any project class the method **instantiates** joins the
   positive-guard channel, so `AddToCartForm(request.POST)` with `min_value=1` in `forms.py`
   bounds the value the view multiplies.
3. **Route reachability** (`route_markers` slot; new TSV column 11 → `Finding.meta.route`):
   names referenced by module-level route-registering calls (markers are matched against
   module-level calls only), classes registered/`as_view()`ed (all their methods),
   decorator-wrapped functions, plus two hops of `callIn`. `unknown` when the project has no
   route markers at all, or when the pack's markers do not describe the target's framework.
   Reported on every finding; **never a gate**.

Four slots added to `schema.json` (v2); `_base` ships them empty (plus `.route(`), the Django
pack fills them from the DRF permissions / generic-views / routers docs. Pack byte cap raised
8 → 16 KB (the per-slot cap of 64 is the flood control). Digests re-frozen: the Django pack
moved from `b38082f8d2b6` (the digest the held-out run scored) to `b5df755be580`.

Every DEV false alarm the held-out log called *structural* is gone, each by the capability it
named: `OrderNoteViewSet.retrieve` / `partial_update` (object permission class on the ViewSet,
via `typeDecl`), `add_to_cart_form` (bound in `forms.py`, via the instantiated class),
`add_to_cart_safe` (validation comparison, via receiver identity). The two bait rows still
standing with `_base`/`flask-sqlite3` are the same `add_to_cart_form` - those packs have no
`min_value=1`, which is vocabulary, and correctly so.

The route flag agrees with the key in **10 of 10 comparable cases** - shopfast with `_base`
(shopfast's `cart.add_item` / `cart.checkout` are genuinely unrouted and the key says so) and
djshop-dev with the Django pack; everywhere else it is `unknown` rather than a guess: `probe/`
has no routes, so all five flags are `unknown`, and djshop-dev scanned with the `_base` or
`flask-sqlite3` pack is `unknown` too, because those packs' markers do not describe Django
routes (they used to read as a wrong `no`; fixed in the 2026-09-15 review, runs `150728`,
`150819`, `150912`, `151005`, `151058`). `bench.run` reports `route_agreement` per run.

Through the API (server mode): shopfast 18.7 s (first scan, warm-up), djshop-dev 14.7 s; the
P7 context section costs a few seconds (`callIn` over every method, twice) on these sizes.

## Held-out: what these changes predict, and why it is not measured here

The P6 held-out log classified `WalletViewSet.statement` (queryset hook), `invoice_detail_safe`
(receiver chain), `refund_line_form` (cross-file bound) and the two validation comparisons as
structural. Capabilities 1 and 2 address four of those five; the receiver-chain case
(`request.user.invoices.filter(...)`) is not addressed - it needs the origin of the *receiver*,
not of the compared value. Re-running `djshop-heldout` now would measure rules written after
reading its failures; the number belongs to a new held-out split (P9 or later). `heldout.log`
still shows exactly one pass on `9b4f52b3f5f1`.
